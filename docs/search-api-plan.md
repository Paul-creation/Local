# 서버 검색 API 계획 (보류 — 게임이 수천 개로 늘면 적용)

작성: 2026-10-04. 지금(게임 약 600개)은 전체 목록을 `/api/games/list`(5분 캐시, 압축 약 50~60KB)로 한 번 받아 브라우저에서 바로 검색·필터한다.
게임 수가 늘어 이 목록이 너무 커지면(대략 압축 200KB 이상, 게임 2,000~3,000개 이상) 아래처럼 서버 검색으로 바꾼다.

## 바꿀 때의 엔드포인트

`GET /api/games/search` — 읽기 전용, 공개 정보만

| 파라미터 | 뜻 | 검증 |
|---|---|---|
| `q` | 검색어 (영어·한국어 이름·별명·태그) | 50자까지, 앞뒤 공백 제거 |
| `cat` | 카테고리 | 파티·협동·퍼즐·서바이벌 중 하나 |
| `tags` | 태그 (쉼표, 하나라도 맞으면) | 최대 10개, `TAG_GROUPS`에 있는 값만 |
| `p` | 인원 구간 | 1인·2인·3-4인·5인 이상·16명 이상 중 하나 (`players=N`은 `playersBucket`으로 변환) |
| `d` | 난이도 | 쉬움·보통·어려움 중 하나 |
| `free`, `sale` | 무료만, 할인 중만 | `1`만 인정 |
| `offset`, `limit` | 페이지 | limit 기본 24, 최대 100 / offset 최대 5,000 |
| `suggest` | 자동완성 검색어 | 결과 최대 6개 (`matchRank` 순) |
| `ids` | 비교 바 복원 (`cmp`) | UUID 최대 3개 |

응답: `{ total, items }` — `items`는 지금 `/api/games/list`와 같은 경량 형식(`flattenGame`).

## 서버 쪽 처리

- 판정 규칙은 지금 브라우저 코드를 그대로 서버로 옮김: `matchesGame`·`normalizeSearch`(검색), 인원 구간 조건(`useGameFilters`의 `filtered`), `getPriceInfo`(할인).
  → 결과·정렬이 지금과 같게 유지됨. 정렬은 지금처럼 `created_at` 최신순.
- 게임 수천 개까지는 전체 목록을 서버 메모리에 5분 캐시해 두고 그 안에서 거르는 게 가장 간단. 그 이상이면 Supabase 쿼리로 내림
  (이름 검색은 `looseIlikePattern` + `ilike`로 후보를 줄인 뒤 `matchesGame`으로 다시 거름, 태그는 `overlaps`, 인원은 `min_players`·`max_players` 범위 조건).
- 캐시: `Cache-Control: public, s-maxage=300, stale-while-revalidate=600`. 같은 조건 주소는 CDN에서 그대로 응답.

## 화면 쪽 변경

- `useGameFilters`가 `filtered`를 직접 계산하는 대신 위 API를 부르고, 결과 개수는 `total`을 씀.
- 검색어·필터가 바뀔 때 0.1~0.3초 로딩, 자동완성은 입력이 0.15초 멈추면 요청, "더 보기"는 다음 페이지 요청.
- 뒤로가기 스크롤 복원: 저장해 둔 개수(`list_count`)만큼 처음 요청의 `limit`을 늘려서 받은 뒤 스크롤.
- 요청 실패 시 결과 자리에 "다시 시도" 버튼.

## 바꾸면 달라지는 점 (적용 전에 다시 확인할 것)

1. 검색·필터·결과 개수가 즉시 바뀌지 않고 짧은 로딩이 생김
2. 자동완성이 조금 늦게 뜸
3. "더 보기" 때 잠깐 로딩
4. 서버 요청 실패 시 재시도 안내가 새로 생김
