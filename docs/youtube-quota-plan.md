# YouTube 할당량 구조 개선안

작성: 2026-10-05 · 상태: **제안만 (구현 안 함)**. 단기안은 `fix(quota)` 커밋(`0a69a72`)으로 이미 main에 들어감.

## 1. 지금 구조

하루 한도는 10,000유닛이고 태평양 시간 자정(KST 16시, 서머타임 끝나면 17시)에 초기화된다. 모든 작업이 같은 `YOUTUBE_API_KEY`를 쓴다.

| 작업 | 시각(KST) | 엔드포인트 | units/호출 | 하루 사용량 |
|---|---|---|---|---|
| 일간 `fetch-streamer-videos` | 03:00 | playlistItems.list, videos.list | 각 1 (50개 단위) | 상한 200 |
| 일간 `enrich-videos 90` (트레일러) | 03:00 | search.list | 100 | 스팀 영상이 없는 게임만, 최대 90 = 9,000 |
| 하이라이트 | 17:10 | search.list, videos.list | 100, 1 | 게임당 최대 202, 상한 `max(5000, 10000−500−트레일러−200)` |
| 주간 `fetch-coop-videos` | 금 02:00 | search.list, videos.list | 100, 1 | 게임당 101~202, 대상 50개면 최대 10,100 |

- 한도 배분 식은 `fetch-highlight-videos.mjs`(하이라이트·목요일 coop 몫), `run-steps.mjs`(목요일 트레일러 검색 상한), `lib/streamer-videos.mjs`(스트리머 200)에 나뉘어 있다. 공통 상수는 `scripts/lib/quota-plan.mjs`.
- 실제 사용량은 기록하지 않는다. 각 작업이 "다른 작업이 최대 이만큼 쓴다"는 가정으로 몫을 남겨 둘 뿐이라, 가정이 틀리면(새 게임이 몰림, 순위 변동으로 coop 대상 증가, 수동 실행) 한도에 걸린다.
- 세 작업 모두 한도 초과 시 멈춘 지점부터 이어서 하도록 만들어져 있어 데이터가 깨지지는 않는다.

### 단기안(적용 완료)의 효과와 남은 위험

- 목요일(태평양 시간) 하이라이트 상한 = `10000 − 500 − 1,500(트레일러 검색 15개) − 200 − 갱신할 coop × 202`. 일간 트레일러는 목요일에만 `--yt-max=15`.
- 10/8 시뮬레이션(coop 38개 갱신): 최선 4,139 · 보통 6,159 · 최악 9,477 → 모두 한도 안.
- **남은 위험**: 하이라이트가 목요일 17:10에 coop 몫을 계산한 뒤 금요일 02:00 `bulk-import`로 인기 순위가 바뀌어 coop 대상이 늘면(예: 50개 → 최악 10,100) 한도를 넘는다. 이때는 마지막 게임 일부가 다음 실행으로 밀린다.

## 2. 구조안 A — 공유 units 기록

### 목적
작업 사이의 가정(몫)을 실제 사용량으로 바꾼다. 절감되는 유닛은 없고, **초과를 막고 몫 계산을 한곳으로 모으는 것**이 목적이다.

### 설계
- 새 테이블 `api_usage(id, period_pt date, job text, endpoint text, units int, at timestamptz)`. 한도 주기는 태평양 날짜(`period_pt`)로 구분. 새 기록 테이블이라 삭제 코드를 만들지 않는다(CLAUDE.md의 기록 테이블 삭제 금지 규칙과 충돌 없음).
- 공용 `scripts/lib/yt-quota.mjs`
  - `ytFetch(job, path, params, units)`: 지금 세 스크립트에 거의 같은 모양으로 있는 `youtube()` 래퍼(`fetch-highlight-videos`, `fetch-coop-videos`, `fetch-streamer-videos`)와 `enrich-videos`의 직접 `fetch`를 하나로 합친다. 호출 직후 사용량을 메모리에 쌓고, 종료 시(오류 포함) 한 번에 기록한다. 한도 오류(`quota`, `rateLimitExceeded`)도 여기서 한 번 처리한다.
  - `remaining(job)`: `10,000 − 안전 여유 500 − 이번 한도 주기 실제 사용량 − 아직 안 돈 작업의 예약량`.
- 예약량(우선순위 순, 하이라이트가 가장 낮다)
  1. 스트리머 영상: 200(고정)
  2. 주간 coop: `min(갱신 필요, 45) × 202`, 금요일 한도 주기에만
  3. 트레일러: `min(대기, 90) × 100`. 목요일 한도 주기에는 `THU_TRAILER_YT_MAX × 100`
  4. 하이라이트: 위를 뺀 나머지
- "아직 안 돈 작업"은 작업별 예상 실행 시각과 이미 기록된 사용량으로 판단한다. 예: 하이라이트는 같은 주기에 이미 `job='streamer'` 기록이 있으면 그 몫(200)을 예약에서 뺀다.
- 한계
  - YouTube는 남은 할당량을 알려 주는 API가 없다. 기록은 `ytFetch`를 거친 호출만 잡는다. 콘솔·임시 스크립트의 사용은 안 잡힌다(scratchpad 스크립트는 `ytFetch`를 쓰도록 관례로 둘 수 있음).
  - GitHub 스케줄 지연으로 실행 순서가 뒤바뀌면 예약 가정이 틀릴 수 있어, 예약은 "아직 안 돈 작업" 판단을 기록 기반으로 해야 한다.

### 규모
테이블 1개, 라이브러리 약 60줄, 스크립트 4개의 래퍼 교체. `scripts/security-check.mjs`의 테이블 권한 점검 목록에 `api_usage`를 추가해야 한다(서비스 키 전용, 공개 읽기·쓰기 없음).

## 3. 구조안 B — search.list → playlistItems 전환

### 지금 channel 기반 search.list는 없다
채널의 최신 영상을 search.list로 가져오는 곳은 없다. 스트리머 영상은 이미 `playlistItems`(`UU` + 채널 ID, channels.list 불필요)를 쓴다. **즉 단순 치환으로 줄어드는 양은 0이다.**

### 작업별 전환 가능성

| 작업 | 전환 가능? | 이유 |
|---|---|---|
| 하이라이트 | 어려움 | 어느 채널이든 조회수 순 클립을 찾는 구조라 채널 목록이 정해지지 않는다 |
| 트레일러 (`enrich-videos`) | 불가 | 스팀 공식 영상을 먼저 쓰고 YouTube는 스팀 영상이 없을 때만 쓴다. 게임별 공식 채널 ID가 DB에 없다. 있다면 100 → 1~2유닛이지만 확보 비용이 크다 |
| 합방 (`fetch-coop-videos`) | 가능(채널 목록 필요) | 현재는 한국어 게임명 + "합방·멀티·같이"로 **전체 YouTube를 검색**(스트리머 채널 안 검색이 아님). 합방을 자주 하는 한국 채널 목록을 만들어 업로드를 받아 제목으로 매칭하면 검색을 대체할 수 있다 |

현재 스트리머 채널 36개로는 부족하다: `streamer_videos` 224개 중 coop 대상 50개와 겹치는 게임은 4개뿐(2026-10-05 조회).

### 합방 전환 절감량 계산 (추정)

가정: 채널 50개, 채널당 평균 업로드 800개, 게임명은 제목으로 매칭.

| 항목 | 현재(검색) | 채널 방식 |
|---|---|---|
| 첫 실행(38게임 갱신) | 3,838~7,676 | 처음 전체 스캔: 채널당 `(800÷50) × 2 = 32` → 50채널 약 1,600 (1회) |
| 정상 상태(30일 갱신, 주당 약 11.7게임) | 주 1,180~2,360 (평균 약 1,700) | 주당 채널당 약 2유닛 → 약 100 |
| 절감 | | 주당 약 1,600 (약 90%), 하루로 환산하면 약 230유닛 |

- 한계: 채널 목록을 사람이 정해야 하고, 목록 밖 영상은 못 찾는다. 지금의 Haiku 판단(같은 작품·여럿이 같이 플레이)을 그대로 쓸 수 있는지는 후보 품질에 달렸다.
- 절대량이 작다. 하루 한도의 대부분은 하이라이트 백로그와 트레일러가 쓴다. 전환은 우선순위가 낮다.

### 참고: 벤치마크 채널 방식 실험(2026-10-05)
PC 사양 체커용으로 "게임별 하드웨어 벤치마크 영상 → GPU 등급" 가능성을 두 방식으로 측정했다.

| 방식 | 비용 | GPU 읽힘 | 3060급±1 | 1060급±1 |
|---|---|---|---|---|
| 게임별 검색 20게임 × 25개(500개) | 2,020 | 242 (48%) | 72 (필터 후 46) | 37 (필터 후 30) |
| 채널 5개 × 최근 500개(2,500개) | 351 | 1,594 (64%) | 12 | 10 |

- 유닛당 수확은 비슷하다. 채널 방식은 최근 500개가 신작·신형 GPU에 쏠려 구형 GPU(1060급)가 적다. 전체 업로드로 늘리면 playlistItems는 50개당 1유닛이라 거의 공짜다.
- 채널 10개 전체 업로드 + 약칭 매칭 + 노출 게임 전체 측정은 별도로 진행 중이며, 결과는 이 문서가 아니라 측정 보고에 따른다.
- 게임 검색에서 걸러야 할 잡음: 다른 게임(Elden Ring **Nightreign**, Left 4 Dead **1**, Half-Life **1**), 게임명 없는 영상, 60초 미만 Shorts·1시간 초과 VOD, 채널명의 "Benchmark"에 걸린 무관한 영상(Portal 검색의 콜센터 교육 영상 등).

## 4. 부수 계산

- 하이라이트 백로그: heat_rank 387개 중 갱신 필요 351개 × 게임당 평균 약 159유닛(10/4 실행: 31게임 = 4,935유닛) ≈ 55,800유닛 → 하루 약 5,000이면 약 11~12일(10/17~20쯤 정상 상태).
